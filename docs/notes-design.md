# Notes: design

Status: **phase 1 done, phase 2 in progress**. Last updated 2026-10-20.

## Goals
- A **Notes** app in Hades: titled Markdown documents organized in folders, created, edited and deleted in the browser.
- **Hades is the source of truth.** Obsidian gets copies through a manual CLI `push` / `pull`. There is no live sync.
- **Semantic search** over notes. It returns matching notes with the best snippet and the heading it sits under. Clicking a result opens the note.

**Not in scope for now:**
- Live or plugin-based Obsidian sync.
- Searching journal entries.
- Q&A or "ask my notes".
- Images and attachments. The storage layout leaves room for them.

## Architecture
```
Browser / hades CLI ──► CloudFront /api/* ──► Hades API (Rust Lambda)
                                                │        │          ▲
                                     content    │        │ metadata │ search: embed query
                                                ▼        ▼          │        + QueryVectors
                                     S3 notes bucket  DynamoDB    S3 Vectors index "notes"
                                     (versioned)      NOTE#<sub>        ▲
                                                         │              │ Put/DeleteVectors
                                       DynamoDB stream   │              │
                                       (NOTE# items)     ▼              │
                                                   Indexer Lambda ──► Bedrock Titan Embed V2
                                                   (failures → SQS DLQ)
```

## Storage
### Content: S3
- **Bucket:** name generated by CDK. It has versioning on, SSE-S3 encryption, all public access blocked and SSL enforced, and is kept (`RETAIN`) if the stack is deleted.
- **Old versions:** a lifecycle rule expires non-current versions after 90 days.
- **Key:** `users/<sub>/notes/<path>`, e.g. `users/1a2b…/notes/Projects/Hades/Design.md`.
  - `<path>` is the note's ID: a vault-style relative path ending in `.md`.
  - It mirrors Obsidian folder structure, so `hades notes pull` writes files at the same relative paths.
  - A future `users/<sub>/attachments/…` prefix leaves room for images.
- **Versioning** gives a free edit history. A "History / restore" UI can come later.

### Metadata: DynamoDB (existing table)
| Key | Value |
|---|---|
| `pk` | `NOTE#<sub>` |
| `sk` | `<path>` |
| `title` | Taken from frontmatter `title`, else the first `# H1`, else the filename |
| `project` | From frontmatter `project`; optional |
| `tags` | From frontmatter `tags`; a list, optional |
| `contentHash` | sha256 of the content: used for change detection and optimistic locking |
| `s3VersionId` | Links the metadata to the exact S3 object version |
| `size`, `createdAt`, `updatedAt` | |
| `indexedHash` | (Phase 2) The hash most recently indexed. `indexedHash != contentHash` means "indexing pending" |

- The notes list is a single `Query(pk = NOTE#<sub>)` with no S3 listing. Folder browsing uses `begins_with(sk, "Projects/")`.
- The journal is unaffected (`JOURNAL#…` items).

### Path rules
The rules are defined in `API_CONTRACT.md` and validated in one place on the server. In URLs the path goes in as normal path segments, each percent-encoded on its own: `/api/notes/Projects/My%20Ideas/Design.md`. Encoded `%2F` is avoided because API Gateway and CloudFront can normalize it.

## API
The authoritative spec is in [`API_CONTRACT.md`](../API_CONTRACT.md), under "Notes". In summary:

| Method & path | Purpose |
|---|---|
| `GET /api/notes?prefix=` | List metadata, sorted by path |
| `GET /api/notes/{path...}` | Metadata plus `content` |
| `PUT /api/notes/{path...}` | Create (no `baseHash`) or update (`baseHash` = last-seen `contentHash`) |
| `DELETE /api/notes/{path...}?baseHash=` | Delete the note (S3 delete marker plus the metadata item) |
| `POST /api/notes/move` | Rename or move |
| `GET /api/search?q=&project=&limit=` | (Phase 2) Semantic search |

**Concurrency is optimistic:** a write whose `baseHash` no longer matches gets `409` with the current hash, and the editor offers "reload" or "overwrite".

## Indexing (phase 2)
**Trigger:** the table's **DynamoDB stream**, filtered to `NOTE#` items, feeds the indexer. Failed records retry, then go to an SQS dead-letter queue.

This changed from the original plan, which triggered on S3 events. The S3 object is written *before* its metadata, so an S3 event could arrive while the metadata doesn't exist yet. The indexer would skip the note, and no second event would ever come. Stream records fire only after the metadata commits, and they carry the exact `s3VersionId` and `contentHash`. Every write path, including the CLI, goes through the metadata, so nothing is missed.

**Indexer Lambda:** Rust, sharing the backend crate's models. It is a separate binary in the same workspace. For each message:
1. Take `(sub, path)` from the record's key. On REMOVE, go to step 6, using the old image's `chunkCount`.
2. If the new image has `indexedHash == contentHash`, there's nothing to do. This makes retries, duplicates and the indexer's own write-back safe.
3. Fetch the exact S3 version (`s3VersionId`) and strip the frontmatter.
4. Chunk it by heading sections. A section over about 700 tokens is split on paragraphs with about 80 tokens of overlap, and very small sections are merged. Each chunk keeps its heading path, e.g. `Design > Storage`.
5. Embed each chunk with Bedrock `amazon.titan-embed-text-v2:0` at **1024 dimensions, normalized**. Then `PutVectors` with:
   - Key: `<sub>#<path>#<n>`.
   - Filterable metadata: `sub`, `path`, `project`.
   - Non-filterable metadata: `heading`, `snippet` (the first about 300 characters of the chunk), `updatedAt`.
6. Delete stale vectors: keys `#<n>` at or above the new chunk count, or all of them on delete. Write `chunkCount` and `indexedHash` back under the condition `contentHash = <indexed hash>`, so a note edited mid-index is never marked as indexed.

**Vector index:** one S3 Vectors bucket with one index `notes`: `float32`, dimension 1024, `cosine`, and `heading` / `snippet` / `updatedAt` declared non-filterable. Both are created in CDK (`aws_s3vectors.CfnVectorBucket` and `CfnIndex`).

## Search (phase 2)
`GET /api/search?q=…&project=…&limit=10`:
1. Validate `q`: 1–500 characters.
2. Embed `q` with the same model and dimensions.
3. Call `QueryVectors(topK = 30, filter = { sub: <caller's sub> [, project] }, returnMetadata = true)`.
   - **The `sub` filter is added by the server in one function** and is never taken from the request. This is the only thing isolating users from each other, so it gets a dedicated test.
4. Group the results by `path`. Each note's score is its best chunk's score, and it returns that chunk's `heading` and `snippet`. Sort, then trim to `limit`.
5. Merge in exact or prefix matches on title and path from the metadata Query, ranked first. That way, searching for a note's name always finds it.
6. Join with metadata for `title`, `project` and `updatedAt`. Drop any hit whose note no longer exists, which covers a deletion still in flight.

Response:
```json
[{ "path": "Projects/Hades/Design.md", "title": "Design", "project": "hades",
   "score": 0.83, "heading": "Design > Storage", "snippet": "Content lives in S3…", "updatedAt": "…" }]
```

## Frontend
A new **Notes** entry in the `applications` side-nav, with these routes:
- **`/notes`:**
  - A table of all notes (title, folder, project, updated), with a text filter and a "New note" button.
  - (Phase 2) A search box above it. Results show the title, a path breadcrumb, the heading and a snippet, and clicking one opens the note.
- **`/notes/new`:** you enter a title and folder. The path defaults to `<folder>/<title>.md` and can be edited, and the editor opens empty.
- **`/notes/*path`:** the editor.
  - Markdown in a `Textarea`, with Edit / Preview tabs. Preview uses `react-markdown` + `remark-gfm`, and raw HTML is disabled.
  - **Save is explicit**, with a Save button and Ctrl/Cmd+S. There's no autosave, so each save is one S3 version and one re-index. Save sends `baseHash` and handles `409` with reload / overwrite / copy-my-version.
  - Move/rename, delete (with confirmation) and Copy as Markdown.
  - Unsaved-changes guard.
- **(Phase 2) Indexing status:** an "Indexing…" indicator while `indexedHash != contentHash`.

## CLI (`hades`), phase 3
A small Rust binary in the backend workspace, so it shares types.
- **Auth:** `hades login` does Cognito `USER_PASSWORD_AUTH` and stores the refresh token in `~/.config/hades/credentials` (mode 600). Access tokens are refreshed automatically. The refresh token lasts 30 days by default.
- **`hades notes pull <vault-dir>`:**
  - Downloads every note whose `contentHash` differs from the local file's sha256.
  - Writes a `.hades-sync.json` manifest recording `path → hash` at the last sync.
  - Local files changed since the last sync are **not overwritten**. They're reported as conflicts unless `--force` is given.
- **`hades notes push <vault-dir> [--prefix Folder/]`:**
  - Uploads local `.md` files that changed since the last sync, using `baseHash` from the manifest. A `409` is reported as a conflict, never silently overwritten.
  - Notes deleted locally are only deleted remotely with `--delete`.
  - Skips `.obsidian/`, `.trash/` and anything in a `.hadesignore`.
- `--dry-run` on both prints the plan without changing anything.

## Infrastructure (CDK)
- **Phase 1:** the notes S3 bucket; a `NOTES_BUCKET` env var on the API Lambda; IAM for object read and write, including versioned get and delete.
- **Phase 2:**
  - A DynamoDB stream (`NEW_AND_OLD_IMAGES`) on the table, plus an SQS dead-letter queue for failed records.
  - The S3 Vectors bucket and index.
  - An indexer Lambda (`RustFunction` binary `indexer`, arm64, DynamoDB stream source filtered to `NOTE#`, partial batch failure reporting).
  - IAM for `s3vectors:QueryVectors`, `PutVectors` and `DeleteVectors`, and `bedrock:InvokeModel` on Titan V2.
- Region `us-west-2`. S3 Vectors and Titan Text Embeddings V2 are both available there. Bedrock model access for Titan V2 must be enabled in the account.

## Cost (rough, few-thousand-note vault)
- **Embeddings:** an initial index of about 1–2M tokens costs about $0.02–0.04. Ongoing edits are negligible.
- **Everything else:** S3 storage and versions, S3 Vectors storage and queries, SQS and Lambda come to cents per month.
- **No always-on components.**

## Phases
1. **Notes CRUD:** the bucket, the metadata, the API (without search), the Notes UI with editor and preview.
2. **Indexing and search:** the vector bucket and index, the SQS queue, the indexer, `/api/search`, the search UI, and the indexing-status indicator.
3. **CLI:** `hades login` and `hades notes pull` / `push`.
4. **Later:** a version history UI, attachments, journal search, "ask my notes", an Obsidian plugin.
